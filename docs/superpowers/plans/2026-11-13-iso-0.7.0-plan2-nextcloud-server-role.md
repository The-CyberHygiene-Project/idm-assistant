# ISO 0.7.0 Plan 2: the NextCloud server role

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** a CHP server with `DOCUMENTS=yes` runs NextCloud as the site's local, offline, Kanidm-signed-in CUI store
(team folders with sharing off, tag by folder, copy-out block, audit in Wazuh, nightly backup and checks), built
as signed product packages; plus the fapolicyd fixes the spike found.

**Architecture:** product versions of the spike (`lab/docs-spike/`, "Plan 2 inputs"): a `nextcloud-chp` RPM
(NextCloud + bundled apps + `chp_foldertag`), a `chp-documents` RPM (units, egress, web/PHP config, fapolicyd rule,
monitor checks, Wazuh rules), and a chp-site `documents` module (`chp-site documents enable|check|status`) that
configures everything idempotently on the server, mirroring `security.py`. Plan 3 adds the document workflow
(ledger, server-side publish, `chp-site doc`, marking, ONLYOFFICE and its gates G2-G4, approval alerts for owner
decision 9, guide/SSP/POA&M text incl. decisions 2, 6 and 8); Plan 4 builds the ISO and runs the full gates.

**Tech Stack:** Rocky 9.8 (FIPS, SELinux, fapolicyd, CUI profile); NextCloud 35.0.3 + groupfolders 23.0.1,
files_accesscontrol 6.0.1, user_oidc 8.13.0; PHP 8.3 (`php:8.3`), PostgreSQL 16, httpd + mod_ssl + php-fpm, APCu;
Kanidm 1.11 OIDC; Wazuh 4.14.9; nftables; Python 3.9 stdlib (chp-site); bash; pytest.

**Spec:** `docs/superpowers/specs/2026-11-12-iso-0.7.0-design.md` (§11 holds the owner's nine decisions and the
spike's accepted amendments). **Evidence:** `lab/docs-spike/SPIKE-NEXTCLOUD.md` ("Plan 2 inputs" M1-M7, G1-G4).

## Global Constraints

- Packages Rocky-signed (PHP, PostgreSQL, httpd) or our own signed RPMs; NextCloud code under `/usr/lib/nextcloud`
  (fapolicyd filter); app store, update check and every outbound feature off; no temporary internet access, ever.
- NextCloud never reaches the internet: settings off + nft table `inet chp_nextcloud_egress` matching the apache uid
  (loopback and the server's own address only; log `CHP-NC-EGRESS` and reject) + **no DNS for apache** + names from
  `/etc/hosts` rendered from site config + php-fpm/httpd `BindsTo=` the egress unit with an `ExecStartPre` table check.
- HTTPS on **8443**, LAN only (`SUBNET_CIDR`), at `files.<DOMAIN>`, certificate from the site's step-ca with renewal.
- Sign-in through Kanidm OIDC (user_oidc, ES256, PKCE S256, `chp_groups` claim: `cui-users`, `doc-reviewers`,
  `chp-users`); login page goes straight to Kanidm; one break-glass NextCloud admin (bcrypt; `/login?direct=1`), its
  secret escrowed to the site stick; host sign-in unchanged (row 36 3/3).
- Team folders: CUI, FCI, Archive for `cui-users`; Operations, Internal, Public for `chp-users`; advanced
  permissions on; **share permission off on CUI, FCI, Archive**; reviewers read-only **on CUI, FCI and Archive only**
  (owner decision 7); a reviewer sees CUI only if also in `cui-users`.
- Tag by folder (`CUI`, `FCI`, restricted system tags) on create/write/copy/rename; **copy/move out of CUI, FCI,
  Archive refused, except CUI ↔ Archive allowed** (owner decision 3); refusals and app-disable to the audit log.
- Browser editors off (Text, Office); view and download only.
- Wazuh from day one: share attempts on CUI/FCI, tag/canary failure, app disabled, egress tripped → level 12
  (`ALERT_HOOK`); failed sign-ins, CUI/FCI deletions, downloads from CUI (owner decision 2: audited) → level 7/3.
- `DOCUMENTS=yes` requires `SECURITY_ADDONS=yes` and a server installed with the sized layout (`/data` is its own
  mount); otherwise refused with a plain message. New site keys are optional and additive.
- Server VM memory 8 GiB (lab); guide states the requirement.
- fapolicyd (owner decision 1): `allow_filesystem_mark = 1` shipped in 0.7.0 after a per-role trial with whatever
  rules the trial needs; denial gates and the shipped collector count with `fapolicyd-cli --check-status` (read
  after a fapolicyd restart); a monitor alarm on `fapolicyd.service` failed on every host.
- Build host (owner decision 4): a dedicated build VM on aero; aero's fapolicyd is not changed; never the Mac.
- chp-site stdlib-only, Python 3.9. No secrets in the repo.

## Review Focus

- `documents enable` re-run on a host where it already succeeded → no change, no duplicate folders, OIDC clients
  or tags (`test_enable_is_idempotent`, Task 5).
- The egress table missing at boot, or deleted while running → php-fpm/httpd do not start, or check 79 alerts within
  one monitor run (Task 4 + Task 9 proof).
- A rename or subfolder move inside CUI, and trash/version restore across folders → allowed and still tagged, or
  refused, never untagged (Task 3 tests + Task 9 proof).
- The tag check when `chp_foldertag` is disabled → still runs (from chp-site, SQL) and alerts
  (`test_tag_check_works_without_the_app`, Task 6).
- `fapolicyd.service` failed after two back-to-back package installs → check 80 alerts (Task 8 test + Task 9 proof).

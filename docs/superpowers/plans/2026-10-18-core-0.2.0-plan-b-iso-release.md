# Core 0.2.0 Plan B: ISO 0.2.0, Gates 1–3, Release — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build ISO 0.2.0 with AIDE in the core. Prove it installs a server and two clients from nothing, each with a
first-boot baseline that stays quiet for a full day (gate 1). Pass the 11-scenario regression (gate 2) and the CUI scan
with every failure decided (gate 3). Then release it to the For Jeff share beside 0.1.0, with the upgrade note and the
0.2.0 site-stick kit.

**Architecture:** This plan reuses the 0.1.0 machinery (ISO Plans 5a/5b) unchanged wherever possible:
- `build-iso.sh`, `check-iso.sh` and the signed-repo tools on aero;
- `lab/iso5/prove.sh` stages, the `lab/iso5` reset and golden-snapshot method, and the engine with `IDM_PROFILE=appliance`;
- `release-iso.sh`.

There are three kinds of new work:
- **Product:** the kickstarts install and enable `chp-integrity`, and one more measured exclusion (`chp-integrity 0.1.3`).
- **Lab:** the stick stays in through first boot, as the 0.2.0 guide now tells sites to do. `prove.sh` checks the
  baseline, pin and quiet check on fresh installs.
- **Release:** the release scripts take the version as a variable, so 0.1.0's published folders are never touched.

**Tech Stack:** bash, Python 3.9 stdlib (`chp_site`), pytest on the Mac (`.venv/bin/python -m pytest -q`), libvirt/OVMF
VMs on aero, OpenSCAP + SSG, gpg with the project YubiKey.

**Spec:** `docs/superpowers/specs/2026-10-12-core-0.2.0-aide-design.md` (§9 gates, §10 build and release, §7 upgrade
note). Also read `lab/aide/PROOF-RECORD.md` ("Not proved here (carried into Plan B)") and Plans
`2026-10-10-iso-plan5a-iso-build-install.md` / `2026-10-11-iso-plan5b-regression-release.md`, whose stages this plan
re-runs.

## Facts established while planning (2026-10-18)

These were measured on the golden iso5 hosts or read from the code:
- **The stick is blocked at first boot.** USBGuard on an installed host has `PresentDevicePolicy=apply-policy`,
  `ImplicitPolicyTarget=block`, and a one-line `rules.conf` that does not name the stick. So a stick left in after the
  install is **blocked** at first boot, which is the state `chp-site stick-pin-hash` reads.
- **The lab installer removes the stick too early.** `lab/iso5/install-iso.sh` detaches the stick right after the
  install, **before** first boot. In the lab this would skip the pin-before-baseline step and raise the one-time
  alert. The lab must instead follow the guide: the stick stays in until the baseline is built.
- **No install-time AIDE database.** The installer's OSCAP addon applies the **stock** CUI profile, where the AIDE rules
  are not selected. No database is built at install, so `chp-aide-baseline.service` (`ConditionPathExists=!` the
  database) still runs at first boot. The dc2 tailoring, which selects the 8 rules, is used only by the gate-3 scan.
- **The package's existing-host branch doesn't run on a fresh install.** `chp-integrity`'s `%post` only takes that
  branch when `server.done` or `client.done` exists, so the kickstart must enable the two units itself.
- **`export-client` would alert on a fresh server.** It empties `/root/chp-escrow-pending` after the first-boot
  baseline, and stock `/root NORMAL` content-checks that folder. The result would be an alert on every new server, and
  SHA-512 hashes of the recovery secrets in the AIDE database.
  - **Owner decision 2026-10-18:** exclude it. Monitor check `40-escrow-pending` covers it instead (Task 1).
- **AIDE alerts can't break gate 2.** The diagnostic engine does not read monitor alerts.
- **The stick can stay attached safely.** `lab/iso2/stick.sh escrow` mounts the stick image **read-only**
  (`loop,ro`), so the unlock helper can read it while the VM has it attached.
- **The iso5 hosts are replaced.** Owner decision 2026-10-18: gate 1 reinstalls iso5-srv, cli1 and cli2 from the 0.2.0
  ISO and takes new golden snapshots; no 0.1.0 copy is kept. Plan A's upgrade proof stays in
  `lab/aide/PROOF-RECORD.md`.

## Review Focus

1. **A first boot where the stick is not blocked:** for example, a real machine whose USB controller is re-enumerated,
   or a policy file that changed. Expected: no hash is pinned, the baseline is still built, and the first stick use
   raises one alert that is accepted. It must not fail first boot, and it must never authorize the stick. → Task 3
   check `"$vm: stick blocked during first boot"`, plus the existing unit test
   `test_blocked_site_stick_hash_is_pinned_without_allowing_it`.
2. **The daily AIDE check (about 22 min of CPU) running while gate 2 runs:** expect correct but slower scenarios, not
   timeouts. → Task 6 Step 2 records each host's timer time and the regression's start and end.
   - If a scenario fails while `chp-aide-check` is active, re-run that scenario before treating it as a product cause.
3. **The 24-hour quiet window on a fresh install:** a daily timer could fire before the clients are pinned, giving only
   a first check that covers a few hours. Expected: the verdict waits for the second run after the **last** pin. →
   Task 3 stage `quietcheck` compares the check's start time with the recorded T0 and refuses an early check.
4. **The escrow folder after export:** no AIDE entry for `/root/chp-escrow-pending` or its files. → Task 1 static test,
   and Task 5's `aide --path-check` on iso5-srv.
5. **`release-iso.sh` for 0.2.0 must never write into `0.1.0/`:** expect a refusal if the target exists, and the 0.1.0
   values exactly as before when `V=0.1.0`. → Task 7 static tests `test_release_script_versions_are_parameters` and
   `test_release_kit_never_touches_the_0_1_0_kit`.

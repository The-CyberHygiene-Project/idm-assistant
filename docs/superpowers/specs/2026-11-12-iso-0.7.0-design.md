# ISO 0.7.0: NextCloud document store and controlled-document workflow (design)

**Status:** APPROVED by the owner 2026-11-12 (builder-check questions answered the same day). Decisions below marked **(owner)** were made in conversation on
2026-11-12; **(my call)** are the designer's defaults the owner may override; **(builder)** is left to the builder.
**Builds on:** ISO 0.6.0 (`2026-11-09-iso-0.6.0-design.md`: disk layout with `/data` and `/backup`, check 76),
the security bundle (Wazuh, YARA, Suricata, the daily security review and its sign-off ledger). **Model:** the
diwai reference system (RS#2), which uses NextCloud as its canonical CUI store and controlled-document manager.

## 1. Purpose

Give a CHP site **one local, canonical store** for CUI and for the system's own controlled documents (SSP,
POA&M, policies, procedures, runbooks, change records, evidence), and **a controlled way to change them**: written
on an encrypted workstation, approved by someone other than the author, published one way into the store, marked
and tagged so CUI cannot leak, and fully audited (NIST SP 800-171 3.1.3, 3.1.22, 3.3.1, 3.4.3, 3.8.4, 3.8.9,
3.13.8).

**Success:** a site installed from 0.7.0 with `DOCUMENTS=yes` has NextCloud on its server; users sign in with
their existing Kanidm account and authenticator code; an author checks out, edits in ONLYOFFICE Desktop, gets a
delegate's approval and publishes; the published file is marked, tagged, versioned, audited in Wazuh and backed
up nightly; and every attempt to expose CUI is refused and alerted.

**Anti-goals (owner) — a failure even if every test passes:**
- **CUI leaking through a share link (public or internal), or through a file that escaped tagging.**
- **NextCloud able to reach the internet.** It is local only: no app store, update check, federation, push,
  recommendations, link previews or any other outbound call.
- **CUI crossing the network boundary by anything but a secure method.** NextCloud listens on the site LAN only.
- **Remote or collaborative editing over a VPN.** Not built. That is a big step the system owner takes once the
  system is running, not the project.

**Non-goals:** in-browser editing (owner: off); ONLYOFFICE Document Server or Collabora; the NextCloud desktop sync
client; external or federated sharing; NextCloud on workstations; upgrading existing installs (§9); a carry-over
of accounts or ledgers from older installs (owner: no site needs it).

## 2. Where it runs (owner)

- **On the CHP server**, files on the **`/data`** volume (0.6.0 layout; 350 GiB on a 2 TB server, grown with the
  grow-a-volume runbook). A server installed on a disk below 900 GB has no `/data` volume: `DOCUMENTS=yes` is refused
  there with a plain message **(my call)**.
- Turned on by a new, optional, additive site key **`DOCUMENTS=yes|no`** (default `no`) **(my call)**. It requires
  `SECURITY_ADDONS=yes`, because the audit trail goes to Wazuh.
- **Packages (my call):** NextCloud as our own signed RPM, so fapolicyd trusts it, with the NextCloud apps it needs
  bundled in (the app store is off). Everything else (web server, PHP, database, cache) comes from Rocky 9,
  Rocky-signed. Database **on the same server**, so there is no second machine NextCloud depends on (a diwai
  lesson). Which database, web server and PHP stream: **(builder)**, from Rocky 9 AppStream, chosen in the spike for
  FIPS, SELinux and fapolicyd fit.
- **Listener:** HTTPS only, on the site LAN only (firewalld limited to `SUBNET`), at a new DNS name in the site zone
  (for example `files.<DOMAIN>`) **(my call)**, with a certificate from the site's step-ca and automatic renewal like
  Kanidm's.
- **No internet (owner):** NextCloud's own settings say it has no internet connection, with the app store, update
  checker and every outbound feature off. That is enforced below the application as well (SELinux booleans and a
  firewall rule letting NextCloud reach only the server itself). A proof shows an outbound attempt refused.
  Mechanism: **(builder)**.

## 3. Sign-in and access

- **Sign-in through Kanidm (owner, 2026-11-12, option 1a).** Today's authenticator codes live on each host (the
  PAM authenticator module, requirements rows 11 and 42) and Kanidm never sees them, so true single sign-on is not
  possible without reworking host sign-in. Instead each user enrols **one more authenticator code, in Kanidm
  itself** (Kanidm's own web credential: password plus TOTP), and NextCloud signs in through Kanidm (OIDC expected;
  protocol **(builder)**, proved in the spike). That Kanidm credential is the one that can later become the only
  one (moving host sign-in to Kanidm codes is a later step, not 0.7.0). Host sign-in (rows 11, 19, 36, 42, 43) is
  unchanged. No local NextCloud passwords for people; one break-glass NextCloud admin, its secret escrowed to the
  site stick like the other recovery secrets. The same Kanidm identity is what the workstation `doc` commands and
  the approval ledger use.
- **Groups come from Kanidm:** `cui-users` (CUI, FCI, Archive), `doc-reviewers`, and all users. Group-folder
  advanced permissions are **on**. **Reviewers (owner, 2026-11-12):** the reviewer role is a read-only layer, never
  a way into CUI: a reviewer sees a CUI or FCI folder only if also in `cui-users`, and then read-only; without
  `cui-users` a reviewer reads only the non-CUI folders.
- **Default folder set (my call, modelled on diwai):** CUI, FCI and Archive for `cui-users`; Operations, Internal
  and Public for all users. Folder names may be changed on the site stick.
- **CUI, FCI and Archive are team folders** (NextCloud's group-folder app) assigned to the Kanidm group
  `cui-users`; membership in Kanidm is the only way in, so adding or removing someone in Kanidm grants or revokes
  access.
- **Sharing (owner, 2026-11-12):** the **share permission is off** on the CUI, FCI and Archive team folders for
  everyone, so no file in them can be shared onward, not even to another NextCloud user. An attempted share is
  refused, logged and alerted (level 12). Elsewhere: no public links to anything tagged CUI or FCI **(my call: FCI
  too)**; no external or federated sharing at all; download limits on.
- **Browser (owner):** view and download only. NextCloud's in-browser editors (Text, Collabora/NextCloud Office)
  are off. This removes the autosave damage diwai saw on a controlled record.
- Sessions time out as the rest of the appliance does; brute-force protection on.

## 4. The controlled-document workflow (owner: hand-off, like diwai)

**Scope (owner, 2026-11-12):** only **controlled documents** (SSP, POA&M, policies, procedures, runbooks, change
records, evidence) go through check-out, approval and publish. They live in a **Compliance** area inside the CUI
folder (and a non-CUI Compliance area for non-CUI controlled documents) that **only `publish` can write to**.
**Ordinary CUI work files** (drawings, data, customer material) are uploaded by `cui-users` through the browser
into the CUI or FCI folders, without approval. **Tagging is by folder, not by file name:** everything in the CUI and
FCI folders is tagged, so nothing gets in untagged; the `CUI_`/`FCI_` name rule applies to controlled documents.
The CUI banner check applies where the target folder is CUI or FCI; non-CUI controlled documents follow the same
workflow without the CUI banner.


**Writing happens in ONLYOFFICE Desktop on the workstation** (owner), on a working copy in the user's home on the
workstation's full-disk encryption (LUKS2, FIPS mode), so the working directory stays compliant (owner). ONLYOFFICE
Desktop ships in our repo as a signed package (fapolicyd), with its vendor calls (templates gallery, plugin lists)
blocked; the only AI it may use is the local model, as at diwai **(my call)**. Whether ONLYOFFICE Desktop runs
cleanly on a FIPS-mode Rocky 9 workstation is a spike question. **If it does not (owner: TBD):** the owner decides
after the spike between waiting for it, switching to LibreOffice from Rocky (templates and checker would follow), or
shipping the store without a desktop editor. ONLYOFFICE's AI features are **off** in 0.7.0 **(my call)**: the
appliance has no local model yet (the Local AI engine is a later component).

Commands on the workstation (names **(my call)**; transport and authentication **(builder)**, with no long-lived
password stored in plain text and no new network port beyond NextCloud's HTTPS):

1. **`chp-site doc checkout <document>`** — fetches the canonical copy to the working folder and records which
   version it came from (NextCloud's own change marker), so a later publish can tell if the canonical copy moved.
2. **`chp-site doc new <title>`** — starts a new document from a **marked template** (§5).
3. **`chp-site doc check <file>`** — reports what is missing: name rule, markings, `-DRAFT`, freshness. Dry run,
   changes nothing.
4. **`chp-site doc approve <file>`** — run by the approver, signed in as themselves. Records approver, time,
   document hash and notes in the **approval ledger** (below).
5. **`chp-site doc publish <file>`** — uploads to its folder, applies the CUI/FCI tag and confirms it took,
   confirms the version, produces the reader PDF, and records the publication. It **refuses** when: the canonical
   copy changed since checkout (diwai's freshness rule); there is no approval matching this exact file hash; the
   file is still `-DRAFT`; the name rule fails; the markings check fails.

**Rules carried over from diwai (my call):** NextCloud is canonical; `CUI_`/`FCI_` prefix, `_vX.Y` versions,
`-DRAFT` while in progress; supersede, never delete (old versions withdrawn to the Archive folder); readers and
assessors get PDFs; a numbered change record for every controlled change; a citation check so nothing still cites a
superseded version **(builder: how far to automate)**.

**Approval (owner):**
- The approver is the ISSO (`ISSO_NAME`) or anyone in `REVIEW_DELEGATES`, and **never the author**. Because a
  typed name is no longer enough, new optional, additive site keys list the **Kanidm account names** of the ISSO
  and the approvers (names **(builder)**) **(my call)**; `ISSO_NAME`, `REVIEW_DELEGATES` and the daily review
  sign-off are unchanged in 0.7.0. A "one-person site" for the override = no approver account other than the
  author's. The author
  is the signed-in user who checked the document out (or created it); the approver must be a different signed-in
  user. A typed name is not enough.
- **ISSO override (owner):** when no delegate exists (a one-person site), the ISSO may approve their own document
  with a recorded reason. The override is **logged, flagged in the next daily review, and alerted at once** through
  `ALERT_HOOK`.
- **Approval ledger (my call):** hash-chained and append-only, kept forever, its head recorded on the site stick at
  each export: the same design as the daily review's sign-off ledger. Where it lives and how a workstation command
  appends to it without a new listener: **(builder)**, after the spike. It must be central (one ledger per site),
  and its entries must carry authenticated identities.

## 5. Marking and tagging (owner asked; diwai's lessons)

- **The approved hash covers the finished, marked file.** Marking happens before approval, never after, and an
  approved or published file is never changed in place.
- **Marked templates:** new Word and Excel documents start from templates with the CUI banner (top and bottom of
  every page) and the designation block (page one) in real header and footer styles, so every page is marked by
  construction. The templates live in the **chp-templates** library (a new document-template set).
- **One source for marking values:** "Controlled by", the default CUI category and the point of contact come from
  new optional site keys on the site stick (names **(builder)**), never typed per file.
- **Checker first:** `doc check`, `approve` and `publish` verify the banner on the first and last page and the
  block on page one, and refuse without them. Insertion is offered only for `-DRAFT` files, before approval, with a
  dry run. Formats: docx, xlsx, md and PDF at least **(builder: how, per format)**.
- **Reader PDFs** are made last, as derivatives of the approved file (stamped if needed); re-exports from an
  unmarked source are refused.
- **Tagging (by folder, §4):** every file in the CUI and FCI folders is tagged automatically on arrival and
  `publish` confirms it. A nightly check lists every file in those folders, and every `CUI_`/`FCI_` file anywhere,
  missing its tag, and alerts. A nightly canary test tries a public link on a CUI
  test file, expects a refusal, and alerts if the refusal fails. Because the rule can be switched off silently,
  the check never trusts it.

## 6. Audit, alerts, review and backup

- **Wazuh from day one:** NextCloud's audit log (JSON) is read by the server's Wazuh agent, with a decoder and CHP
  rules. Level 12 (immediate, `ALERT_HOOK`): any share attempted on CUI/FCI (internal, public or external), the tag or canary
  check failing, an ISSO override, the outbound block tripped. Level 7: failed sign-ins, deletions in CUI/FCI,
  approvals and publications (the daily summary).
- **Daily security review:** a new status section for NextCloud: service, certificate, last backup, tag check,
  canary, overrides since the last review, publications.
- **Monitor checks** for NextCloud's services and certificate (numbers **(builder)**); check 76 already covers `/data`.
- **Backup (my call):** nightly database dump and file copy into `/backup` (encrypted), kept for a set number of days
  (site key), with a restore runbook proved on the lab. The backup-drive runbook (0.6.0) moves it off the server.

## 9. Existing installs (owner)

0.7.0 is **new installs only**. The disk layout and NextCloud's place on `/data` do not fit older installs, and no
site needs a carry-over (the only sites are the lab and one- or two-user sites). An existing site moves by
reinstalling. **(my call)** A short note in the 0.7.0 kit explains how a 0.5.0-update1 site applies the 0.6.0 repo
(0.11.0) to get check 76 and the sign-off fixes without reinstalling, without a full lab proof.

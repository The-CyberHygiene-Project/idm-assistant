# ISO 0.6.0: the disk layout for the recommended server, and the daily review at install (design)

**Status:** draft for owner review (2026-11-09). Layout decisions made in conversation the same day (§2). **Builds on:**
`2026-09-29-chp-appliance-iso-design.md` (the installer), `2026-11-07-security-bundle-review-design.md` (part 4,
released as 0.5.0-update1 / repo 0.10.0, PR #43). **Closes:** requirements row 50 (`lab/iso-requirements.md`).

## 1. Purpose and scope

1. **Disk layout (row 50).** Today `chp-site` renders one layout for every disk: small fixed volumes sized for the
   100 GB minimum (`/var` 20 GB, `/var/log` 8 GB, `/var/log/audit` 8 GB, `/home` 10 GB, swap 8 GB) and `/` grows into
   the rest. On the recommended server (2 TB SSD) that gives `/` about 1.9 TB, where almost nothing grows, while
   everything the security bundle writes (Wazuh, the Kanidm database, Suricata, YARA, a year of reviews) lands in the
   20 GB and 8 GB volumes. XFS cannot shrink and the volume group has no free space left, so this cannot be fixed after
   install. 0.6.0 sizes the layout by the disk.
2. **The daily review at install.** The ISO ships the repo with part 4, so a new install gets the review from first
   boot (as 0.4.0 did for YARA: first boot's `security enable` installs the add-ons; confirm no installer change is
   needed).
3. **Proposed, owner to confirm (§6):** a few of the deferred minors from the part 4 review, and logrotate for
   `chp-yara.json`.

**Success:** a 2 TB server installs with the §2 layout and about 340 GB unallocated; `lvextend -r` grows any volume
online; a lab VM (120 GB) installs as today; a low-space alert reaches `ALERT_HOOK` before any volume fills; the CUI
scan, regression and row 36 stay as in 0.5.0.

**Anti-goals:** repartitioning existing installs (not possible; §5); console prompts during install (the installer
has none, by design); guessing growth figures we have not measured.

## 2. The layout (owner decisions, 2026-11-09)

- **2 TB is the recommended server disk.** The project's documented 2 TB scheme (CHP Phase II hardware
  specification) is guidance, adjusted here.
- **Backups start on the same disk**, with a recommendation (guide + SSP text) to add a separate backup drive. The
  recommended server has a spare drive bay for it.
- **`/backup` gives up room** so `/var` and the logs can grow and the disk keeps headroom; it is its own volume so
  that, when the backup drive is added, the runbook moves backups there and frees the space (§4).

### 2.1 The 2 TB disk (about 1,860 GB usable)

| Volume | Documented scheme | 0.6.0 | Why |
|---|---|---|---|
| `/` | 90 | 90 | |
| `/var` | 30 | **100** | Wazuh, the Kanidm database, a year of reviews |
| `/var/log` | 15 | **50** | Suricata `eve.json` is the main growth |
| `/var/log/audit` | 15 | **30** | a full audit volume can halt the host under the CUI settings |
| `/var/tmp` | (none) | **15** | the CUI scan requires it separate; the scheme omitted it |
| `/tmp` | 15 | 15 | |
| `/home` | 239 | 239 | |
| `/data` | 350 | 350 | |
| `/backup` | 931 | **600** | staging until the backup drive is added |
| swap | 29 | 29 | |
| **unallocated** | 0 | **~340** | grow any volume online when needed |

`/boot/efi` (1 GB) and `/boot` (2 GB) stay as today, outside the encrypted volume group.

### 2.2 The rule (so other disk sizes follow)

- **System volumes are fixed** (`/`, `/var`, `/var/log`, `/var/log/audit`, `/var/tmp`, `/tmp`, swap: 329 GB).
- **The rest R** is split in the 2 TB proportions: `/home` 15.6 %, `/data` 22.9 %, `/backup` 39.2 %, unallocated
  22.3 % (rounded down to whole GB; unallocated takes the remainder). A 4 TB disk therefore gets a larger `/backup` and
  more headroom; a 1 TB disk (931 GiB) gets about `/home` 93, `/data` 137, `/backup` 235, ~134 unallocated. (Sizes are GiB throughout: a 2 TB disk is 1,862 GiB.)
- **Below 1 TB** (lab VMs, evaluation): **today's layout unchanged**, so the lab and the regression stay comparable.
  `/data` and `/backup` are then plain folders on `/`.
- **Below 2 TB** the install log and the install-complete note say "smaller than the recommended 2 TB disk". No
  console prompt.
- The 100 GB minimum stays.

### 2.3 Mount options

`/data` and `/backup`: `nodev,nosuid`; `/backup` also `noexec`. Existing volumes keep the options the CUI
remediation sets today. (Spike step: confirm where those options come from, so the new volumes match.)

### 2.4 Workstations (owner decision, 2026-11-09)

Workstations keep their working data **on the server**, not locally (the reference model: diwai hosts a Nextcloud
server for this). So a workstation gets its **own layout**, never the server's: no `/data`, no `/backup`, a modest
`/home`, and most of the disk left unallocated as headroom.

| Volume | Today | 0.6.0 workstation |
|---|---|---|
| `/` | grows into the rest | **40** (fixed) |
| `/var` | 20 | 20 |
| `/var/log` | 8 | **20** (Suricata and YARA run on workstations too) |
| `/var/log/audit` | 8 | 8 |
| `/var/tmp`, `/tmp` | 4 each | 4 each |
| swap | 8 | 8 |
| `/home` | 10 | **25 % of the rest** (at least 10) |
| **unallocated** | 0 | **the rest** |

On a 512 GB workstation (476 GiB) that is about `/home` 92 and ~277 unallocated. **Below 256 GB** (lab VMs):
today's layout unchanged, as for servers below 1 TB.

**Flag for the guide:** if a site uses a sync client (for example the Nextcloud desktop client) that keeps a full
local copy of the user's files, those files land in `/home` and its size then matters; the guide says to grow `/home`
(runbook, §4) or use the client's on-demand mode. A file service on the CHP server itself is not in 0.6.0; `/data` is
where one would live.

## 3. Implementation outline

- `disks.choose_disk` returns the disk (name and size), not just the name; `render.disk_ks(disk, size, passphrase)`
  computes the server tiers (§2.2) or the workstation layout (§2.4) by role. Sizes in MiB for kickstart `logvol --size`; no `--grow` in the sized layout (the
  unallocated space stays in the volume group).
- Tests: the 2 TB table exactly; 1 TB, 4 TB and 120 GB servers; 512 GB and 120 GB workstations; volume sizes sum to no more than the volume group; the
  unallocated figure; mount options; the below-2 TB note.
- **A second disk at install** (the backup drive already in the bay): the installer already refuses to guess between
  two disks and asks for the install disk in the hosts table (5th column). The guide says so in the backup-drive
  section.

## 4. Space alerts and runbooks

- **Monitor check 76 (disk space), every host, in chp-base** (not only with the security add-on): ALERT when any
  local XFS volume is at or above 85 %, once per crossing; it reports the volume group's free space in the message
  ("grow with lvextend -r; N GB free in chp"). It skips the file system that check 72 already watches for Wazuh, so
  nothing is alerted twice. The daily review already shows disk use per host (sysstat/df).
- **Audit volume:** the spike records what the CUI profile sets for auditd `space_left`, `admin_space_left` and
  `disk_full_action`, and the guide states it plainly (what happens to the host when the audit volume fills).
- **Runbook: grow a volume.** `lvextend -r -L +NG chp/<name>` online; check with `df`; AIDE impact (none: data
  volumes).
- **Runbook: move `/backup` to the backup drive.** Encrypt the new drive (LUKS2, bound to the TPM like the system
  disk, recovery passphrase escrowed to the site stick), make its file system, copy, switch the mount, then remove
  `chp/backup` so its space returns to the volume group. Proved on the lab by adding a virtual disk to srv.
- **Guide and SSP text:** the recommended disk and the backup-drive recommendation in the site-stick guide; check the
  chp-templates narratives that describe storage or backups (e.g. 3.3.4, 3.8.9) and update them if they state the
  layout.

## 5. Existing installs

Not repartitioned. Their volume group has no free space (`/` took it), so the new layout reaches a site only by
reinstalling. Check 76 still applies to them after the update. The notes say this plainly, so a site planning its
first real server (e.g. RS#3 / dc2) installs 0.6.0 or later.

## 6. Proposed additions (owner to confirm)

From the part 4 final review's deferred minors, the ones that matter most once real ISSOs sign:

- two concurrent signers can sign the same day (re-check inside the append);
- piped input counts as sign consent (require a terminal, or an explicit `--yes`);
- a bad `--date` gives a traceback; `--notes` has no length or control-character check;
- the build uses the system timezone while the report and monitor use the site `TIMEZONE`.

Also: `chp-yara.json` has no logrotate (since part 2).

## 7. Releases and gates

- **Repo 0.11.0** (chp-site with the layout and §6 fixes, chp-base with check 76, chp-security if logrotate lands
  there), then **ISO 0.6.0**. Optional 0.5.0-update2 for check 76 and §6 on existing sites: owner's call after the
  build.
- **Spike first:** render the 2 TB layout and install it on a lab VM with a 2 TB **sparse** qcow2 disk on aero
  `/data` (owner decision 2026-11-09). Measured basis: the 120 GB lab disks take 8 to 14 GB on aero; `/data` has
  665 GB free. **50 GB stop:** a watcher polls the image's actual size (`du`) during the install and every proof
  stage and destroys the VM if it passes 50 GB (cause then investigated: some step wrote the whole disk). Confirm
  mount options, the CUI scan, TPM unlock, and `lvextend -r`. Fallback if aero cannot: 1 TB sparse (same code path).
- **Gates:** fresh installs at 120 GB (today's layout), a 2 TB sparse server and a 512 GB sparse workstation; review proofs on a fresh install;
  check 76 catch (fill a test volume past 85 %); the backup-drive runbook on the lab; regression 33/33; row 36 3/3;
  CUI scan 108/2 on every host (any change from the new volumes explained); quiet day.

## 8. Not in 0.6.0

Changing the documented hardware specification itself; automatic growth of volumes; backup software or schedules
(the Kanidm backups path stays as today); the ISSO web portal.

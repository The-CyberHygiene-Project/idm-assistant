# Core release 0.2.0: file integrity monitoring (AIDE)

**Date:** 2026-10-12 · **Status:** APPROVED by the owner 2026-10-12
**Owner:** D. Shannon (System Owner / ISSO)
**Inputs:** requirements row 47 (ISSO 2026-10-11); the ISO spec `2026-09-29-chp-appliance-iso-design.md` (gates,
monitor framework §5.4, `chp-site` §4); the released 0.1.0 (`RELEASE-RECORD-ISO-0.1.0.md`, `lab/iso5/`); the site-stick
kit (`appliance/site-stick-kit/`, `lab/kit/PROOF-RECORD.md`); Rocky 9.8 DVD `aide-0.19.2-5.el9`; SSG RHEL 9 data stream
on aero (rule texts and OVAL checks read 2026-10-12).

## 1. Purpose

Add **file integrity monitoring** to the identity appliance core (NIST SP 800-171 3.14.x / SI-7): detect unauthorized
changes to system files and to the appliance's own security configuration, alert through the existing monitor, and
let a baseline change only through an approved, recorded, off-host-pinned step. Release it as **core 0.2.0** (a new
ISO). The released **0.1.0 stays unchanged**; a 0.1.0 site (dc2) can add AIDE by a signed package update.

**Lesson carried in from dc1 (repo scan 2026-10-12):** dc1's manual and POA&M-008 said AIDE was installed and checking
daily; its SBOM package list has no `aide`, and its tech spec says "AIDE (via Wazuh FIM)". The control existed on paper
only. Therefore every claim here is proved by **AIDE catching a planted change**, not by AIDE being present (§9).

### Success criteria
1. A fresh 0.2.0 install builds its baseline by itself at the end of first boot and pins it to the site stick.
2. A planted change is reported, and alerted through `ALERT_HOOK`, within one daily cycle (proved by triggering the
   check).
3. A new baseline cannot be accepted without a recorded approver who is the ISSO or a named delegate.
4. The three release gates of 0.1.0 still hold with AIDE installed (§9).

## 4. What AIDE watches

### 4.1 Base
Rocky 9.8's stock `/etc/aide.conf` (read from the DVD RPM): `/boot`, `/bin`, `/sbin`, `/lib*`, `/usr`, `/root` with
`NORMAL` (= `R+sha512-m-c`, incl. ACLs, SELinux, xattrs); `/opt` content; a long list of named `/etc` files and
directories with content checks (sudoers, pam.d, security, ssh_config/sshd_config, audit, named, usbguard, pki,
systemd, sysconfig, cron, …); **the rest of `/etc` with `PERMS` only**; `/var/log` as growing logs.

### 4.2 SSG fixes (by the SSG's own remediation, so the scanner recognizes them)
`aide_verify_acls`, `aide_verify_ext_attributes` (acl + xattrs in every group and selection line),
`aide_check_audit_tools` (`auditctl auditd ausearch aureport autrace augenrules` with the attributes the SSG remediation writes),
`aide_use_fips_hashes` (FIPS-approved hashes only). The stock file defines an unused group `ALLXTRAHASHES` containing
`stribog256/512` (GOST); **measure** whether the scanner's non-FIPS-hash test objects to it and remove the line if so.

### 4.3 CHP additions (content, sha512)
The appliance's security configuration that the stock file checks only for permissions, or not at all:
`/etc/chp`, `/etc/kanidm`, `/etc/step-ca`, `/etc/ssh-ca`, `/etc/ssh/sshd_config.d`, `/etc/ssh/chp_user_ca.pub`,
`/etc/authselect`, `/etc/nsswitch.conf`, `/etc/fapolicyd`, `/etc/selinux`, `/etc/idm-collect`, `/etc/systemd/system`,
and **`/var/lib/ssh-ca/keys`** (the user SSH-key registry: onboarding changes it, and an approver should see that).

### 4.4 Exclusions: candidates, settled by measurement
An exclusion is allowed only when measurement (§4.5) shows the path changing by itself in normal operation **and**
another control covers it. Candidates:

| Path | Why it changes | Covered instead by |
|---|---|---|
| `/etc/pki/kanidm` | Kanidm TLS certificate re-issued every 24 h (ACME) | monitor checks `30-kanidm-cert`, `31-renew-timer` (row 24); chain to the pinned root |
| `/root/.cache`, `/root/.step` | Kanidm / step CLI session tokens | short-lived; not configuration |
| `/root/chp-onboard`, `/root/chp-escrow-pending` | onboarding reset tokens; secrets awaiting `export-client` | onboarding audit records; `40-escrow-pending` |
| `/etc/chp/site-stick.hash` | written once at first stick use | **not excluded:** watched `PERMS` only |

Not watched (as in stock): `/var/lib/google-authenticator` (rewritten at each login), the Kanidm database,
`/var/lib/ssh-ca/issued`.

### 4.5 Measurement (settles §4.4)
Install a 0.2.0 candidate server + client in the lab; build baselines; run **2–3 days** unattended plus deliberate
actions: GA logins, the daily certificate renewal, one onboard, one revoke, a `dnf reinstall` of a CHP package. Every
reported path is either one of the deliberate actions, or justified and excluded (a row added to §4.4 with its
covering control), or a design problem to resolve. The final §4.4 is written back into this spec before Plan B.

## 5. Baseline, daily check, alerts

### 5.1 Baseline
- **Fresh install:** the **last** first-boot step (after every role step, so none of them "changes" the baseline):
  `aide --init`, install the new database as `/var/lib/aide/aide.db.gz`, write `/var/lib/chp/aide/baseline`
  (`BUILT_BY=first-boot`). Server: `export-client` pins it. Client: `62-aide-pin` nags until `chp-site aide-pin`.
- **Upgrade (0.1.0 host):** `chp-integrity` `%post` builds it **only if no database exists** (never overwrites);
  `BUILT_BY=package-install`. It proves the host's state at that moment, not at first boot; the release note says so.

### 5.2 Daily check
`chp-aide-check.timer`: `OnCalendar=*-*-* 03:30`, `RandomizedDelaySec=1h`, `Persistent=true`.
`chp-aide-check.service`: `Type=oneshot`, `Nice=19`, `IOSchedulingClass=idle`, `TimeoutStartSec=2h`, runs
`/usr/libexec/chp/aide-check`, which:
1. compares SHA-512 of `/var/lib/aide/aide.db.gz` with `baseline:DB_SHA512` → `DB_MATCH=yes|no` (a mismatch means the
   database was replaced outside `aide-accept`; the check still runs);
2. runs `aide --check`, report to `/var/log/aide/check-<time>.log`;
3. maps the exit code exactly: **0** clean; **1–7** bit flags added (1) / removed (2) / changed (4); **≥14** AIDE
   error (config, database, I/O) → `EXIT` and counts into `last-result`; one summary line to the journal
   (`authpriv`, tag `chp-aide`).

The wrapper never rebuilds or replaces a database.

### 5.3 Monitor checks (existing framework, `monitor.d`; they never repair)

| Check | ALERT when |
|---|---|
| `60-aide-result` | last result has changes, an AIDE error, or `DB_MATCH=no`; or no database exists |
| `61-aide-stale` | no completed check for more than **26 h**, or the timer is not active |
| `62-aide-pin` | `baseline:DB_SHA512` differs from `pinned` (current baseline not on the stick) |

Alerts repeat every monitor run until the cause is gone: changes stop alerting only after `aide-accept`. There is no
"acknowledge" or "silence".

## 6. Operations (`chp-site`)

### 6.1 `chp-site aide-accept --approver NAME --reason TEXT` (root)
1. Refused unless NAME equals `ISSO_NAME` or is in `BASELINE_DELEGATES` (same matching as `unexpire`); refused if
   TEXT is empty.
2. Runs a **fresh** `aide --check` (never trusts an older report) and shows a summary in two groups:
   - **Explained by signed package updates:** paths owned by a package installed/updated after `BUILT_AT`, that
     `rpm -V` reports unmodified, from a package whose signature key is pinned (Rocky, EPEL, project; the same pinned
     list as row 46).
   - **Not explained:** everything else, listed in full.
   The grouping is a reading aid; nothing is accepted automatically.
3. Asks for confirmation (`--yes` for scripted lab use only), then `aide --init`, installs the database, updates
   `baseline` (`BUILT_BY=accepted:<NAME>`).
4. **Audit** before and after (the `unexpire` path: `auditctl -m` user message + `authpriv` log): approver, reason,
   login user (`loginuid`), source address, group counts, old and new `DB_SHA512`. The shown report is kept in
   `/var/log/aide/accepted/<time>.log`.
5. Asks for the site stick and runs `aide-pin`. Without a stick the accept still completes; `62-aide-pin` nags.

**Known limit (as for `unexpire`):** NAME is attested, not authenticated; accountability comes from the audit record
(who was root, from where). Signed approval (e.g. the ISSO's YubiKey) is a possible later change, not 0.2.0.

### 6.2 `chp-site aide-pin` (root)
Stick access exactly as `export-client` (USBGuard: only the pinned stick, temporarily allowed, blocked again). Writes
`aide/<host>.txt`: `HOST`, `DB_SHA512`, `BUILT_AT`, `BUILT_BY`, `PINNED_AT`. An existing record is renamed
`aide/<host>.<PINNED_AT>.txt` first (history kept, nothing overwritten). Then writes `/var/lib/chp/aide/pinned`.
`export-client` calls it on the server.

### 6.3 `chp-site aide-verify-pin` (root)
Reads the newest `aide/<host>.txt` on the stick (same access path) and prints `MATCH` or `MISMATCH` (with both hashes).
For the ISSO's periodic review. `MISMATCH` means investigate; nothing is changed.

### 6.4 `site.conf`
New optional key `BASELINE_DELEGATES` (comma-separated names, same pattern as `UNEXPIRE_DELEGATES`). Sticks made with
the 0.1.0 kit stay valid. The kit template and `SITE-STICK.md` gain the key and the client step "plug in the stick,
`chp-site aide-pin`" after a client's first boot.

## 7. Upgrade path for 0.1.0 sites
On a 0.1.0 host: install the signed repo update (the 0.7.0 repo tarball), `dnf install chp-integrity`. `%post` builds the
baseline (§5.1); the timer and monitor checks start; `62-aide-pin` nags until `aide-pin`. A 0.1.0 `chp-site` lacks the
new commands, so the update includes the new `chp-site`. The 0.2.0 release folder carries a short note for this.

## 8. Compliance (gate 3)
The 8 SSG rules are selected in the tailoring. Expected: **6 pass** (`package_aide_installed`, `aide_build_database`,
`aide_use_fips_hashes`, `aide_check_audit_tools`, `aide_verify_acls`, `aide_verify_ext_attributes`); **2 deviations,
met by equivalent means:**
- `aide_periodic_cron_checking`: the OVAL test accepts only a cron line `/usr/sbin/aide --check` (crontab, cron.d,
  cron.daily/weekly, root's spool). Equivalent: `chp-aide-check.timer` daily, plus `61-aide-stale` (which the cron
  approach does not have). Evidence: §9 catch and stale tests.
- `aide_scan_notification`: the OVAL test accepts only `| /bin/mail -s "…" user@host` on that cron line.
  Equivalent: monitor → journal + `ALERT_HOOK` (no MTA on the appliance). Evidence: §9 `ALERT_HOOK` receipt.

## 9. Testing and proof

**Unit tests:** approver matching; `BASELINE_DELEGATES` parsing; pin-record format and history; explained/unexplained
grouping; exit-code mapping; each monitor check against sample state files.

**Catch proof (installed lab hosts; every row PASS/FAIL):**

| Planted | Expected |
|---|---|
| modified file in `/usr/bin`; edited `/etc/kanidm` config; new file in `/etc/ssh/sshd_config.d` | next check reports each; `60-aide-result` alerts; a test `ALERT_HOOK` script receives the alert |
| database replaced by hand | `DB_MATCH=no` alert |
| timer stopped; result older than 26 h | `61-aide-stale` alert |
| `aide-accept` with an unlisted name / empty reason | refused; database and baseline unchanged |
| `aide-accept` by a delegate | accepted; before + after audit records; alerts stop |
| baseline not pinned → `aide-pin` | `62-aide-pin` alert → record on stick → quiet |
| `aide-verify-pin` on good / tampered database | `MATCH` / `MISMATCH` |
| `dnf reinstall` of a CHP package, then `aide-accept` | its files listed under "explained by signed package updates" |
| 2–3 days of normal operation (§4.5) | only the deliberate actions reported |

Throughout: **0 AVC denials** (AIDE under systemd, the wrapper, `chp-site`), fapolicyd quiet; check duration recorded.

**Upgrade proof:** on a 0.1.0 install (snapshot of the iso5 golden hosts, reverted afterwards), the §7 steps, then the
catch rows for one planted change, accept, pin.

**Release gates (as 0.1.0):** (1) server + 2 clients installed from the 0.2.0 ISO, baselines built at first boot and
pinned; (2) the 11-scenario regression 33/33 + row 36 with `IDM_PROFILE=appliance`; (3) CUI scan with the dc2
tailoring: every failure fixed or in the deviation table (§8).

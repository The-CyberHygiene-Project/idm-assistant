# ISO 0.7.0 known issues

These are the known limits of the 0.7.0 document server and the controlled-document workflow. Each one that needs a
POA&M row has its id (T-08 to T-16); the rows are in `appliance/site-stick-kit/poam-seeds-0.7.0.md`. The user
guide is the chapter "From 0.7.0 on: controlled documents" in `appliance/site-stick-kit/SITE-STICK.md`.

0.7.0 is for **new installs only**. An existing site moves by reinstalling.

## Resolved in 0.7.0-update1 (package update; no reinstall)

- **P3-D16 fixed.** An ISSO override reason of about 2,000 bytes left the level-12 alert for rule 100643 with raw
  `$(dstuser)` and `$(path)`. The journal line the Wazuh decoder reads now carries at most the first 400 bytes of the
  reason (cut on a UTF-8 boundary, ending `...[truncated; full text in the ledger]`), so the person and the document are
  always named. The ledger keeps the whole reason (`chp-site` 0.14.0-13).
- **`chp-templates` is a signed release.** 1.4.0-3 was a lab candidate (pinned by sha256, no signature). 1.4.0-4 is built
  from the signed 1.4.0 release.
- **The POA&M numbers are settled.** The NIST requirement numbers on T-08 to T-16 were marked pending owner confirmation.
  The owner confirmed them on 2026-11-27 (Rev 2 content 1.2.9); the notice is removed from the template library and from
  `poam-seeds-0.7.0.md`.
- Still open: the server's OpenSCAP tailoring is not yet applied by the kickstart (it waits for the next ISO), and P3-D6.

## Limits that stay in 0.7.0

### The database cannot do MD5 (T-08)

PostgreSQL in FIPS mode refuses `MD5()`, which NextCloud uses for some moves. The server refuses those moves
(DEGRADED mode) so that nothing is left half-moved.

- Refused: moving, renaming or deleting a folder with files in it; moving a file that has old versions to another
  team folder.
- Works: files, copies, empty folders, CUI to Archive and Archive to CUI for a file without old versions.
- `chp-site documents status` and the nightly check show "DEGRADED: database MD5 unavailable". The first refusal each
  day raises a level-7 alert.
- A publish of a CUI document is refused, with nothing changed, when the published file has old versions. There is no
  way around it by hand; publish again after DEGRADED ends.
- Moving a file with old versions to another team folder is not supported in 0.7.0.
- The refusal stops by itself when the database can compute MD5. The upstream defect report is the owner's to file.

### fapolicyd filesystem marks are off (T-09)

fapolicyd 1.4.3-3 (Rocky 9.8) exits about a second after a restart with `allow_filesystem_mark = 1`
("recvmesg failed"). The marks therefore stay off (`FSMARK=0`). Files that services open in their own mount
namespace are not checked by fapolicyd.

The same exit can follow any fapolicyd restart, also with marks off. `chp-site documents enable` restarts fapolicyd,
checks it three times, restarts it once more if it is dead, and fails if it is still dead. Monitor check 80 alerts
until it runs again. The trial is repeated when Rocky ships a fixed version.

### The editor's crypto is not validated (T-10)

ONLYOFFICE Desktop Editors bundles Chromium with BoringSSL, which ignores the system's FIPS mode. Chromium runs with
`--no-sandbox`, and the app runs unconfined. The editor makes no network connection of its own: its network features are
blocked, and `chp-site doc` does the transport with the system OpenSSL.

The controls proven so far are the removed AI Tools plugin, the egress table and the hosts block. The settings-file keys
that hide AI entries and turn off plugins and portals are defaults whose effect is not proven.

### PHP 8.3 (T-11)

NextCloud 35 runs on PHP 8.3. Later releases need a newer PHP. The move (a newer PHP stream, or Rocky 10) is planned
before NextCloud 37.

### The OIDC code appears in NextCloud's audit log (T-12)

The sign-in callback's address, with the single-use OIDC `code` and `state`, is written to the audit log and reaches
the Wazuh index. The code is bound to the client secret and to PKCE and expires within minutes. NextCloud's log writer
is not ours to change. Both records are CUI-boundary records.

### The ledger can be forged on the server, and is watched (T-13)

A compromised NextCloud could replay a live approver token. Anyone with a shell on the server can write false
`chp-docs-ledger` journal lines with `logger -t`, and so raise a false level-12 alert. A false line never hides a real
event: check 82 and the daily review trust only the ledger and root's journal lines. Every approval and every ISSO
override alerts at once. The residual is accepted with detection, which needs `SECURITY_ALERT_LEVEL` of 12 or lower:
above that, approvals and overrides reach only the daily summary.

After any Wazuh upgrade, prove again that the ledger lines still reach the level-15 base rule (100640) and its
children, not a stock rule.

### DNS tunnelling through the site resolver (T-14)

A workstation may send DNS to the site resolver, which forwards upstream. DNS to any other server, DNS over TLS and
DNS over QUIC are refused. Data hidden in DNS names to the resolver is not stopped.

### Three accounts live outside Kanidm (T-15)

`chp-publisher` (the ledger appender's account), `chp-canary` (the nightly share test) and `ncadmin` (the break-glass
NextCloud administrator) are local NextCloud accounts. The first two have no usable password. `ncadmin` has one: it is
kept in the site stick's `escrow/` folder, and every sign-in as `ncadmin` pages at level 12 (rule 100622). Record all
three in the SSP and name an owner for each.

### The banner check reads text only (T-16)

A CUI banner in a white or 1-point font passes the check. A missing banner, a banner in a text box, and hidden or
deleted text do not pass. The same holds for the FCI banner of an `FCI_` document.

The other kind's banner is refused anywhere it is looked for, and in Markdown the check fails closed. Some ordinary
lines are therefore refused where they name the wrong kind:
- headings or lines that are just the word or the full name (`# CUI`, `## Controlled Unclassified Information`);
- table cells holding just the word;
- short "word: …" or "word - …" lines of up to three more words (`CUI: see section 3.`);
- the word followed by the full name (`CUI (Controlled Unclassified Information)`);
- the first or last line of a non-CUI Markdown file, and any header or footer line, when it starts with the word
  (followed by a space or any character that is not a letter or digit: `# CUI handling policy`, `CUI SP-PROPIN`,
  `CUI/SP-PROPIN`, even `CUI's ...`) or with the full name, whatever follows (a document name such as
  `CUI_SSP_v1.2` is a citation and passes, but not with `//`, the word, the full name or a capitals marking after it,
  and not with a title that starts with `SP-`; several document names in one line pass the same way);
- any of these in quotes, spelled out letter by letter (`C.U.I.`), with accents, with letters from other scripts
  that look like Latin ones (Cyrillic `Р`, Greek `Ο`: the Unicode confusables data), or split by `<br>`.

The check reads Markdown line by line, so markup that spans source lines (`C<span` and `>UI` on two lines,
`CUI<br` and `class=x>`, `CU` and `I`) is not joined; the reviewer sees these on the rendered page.
Header and footer lines with accented words can be false alarms, because accents are folded away (`Cúi chào`,
`Çui`).
An indented code block inside a list is still checked (it fails closed), so a banner-like line there is refused.
A Markdown line longer than 8192 characters is refused as "cannot be checked" (outside code blocks). The guide
tells authors how to write around them.

Known passes that the check does not catch yet (Task 12b, final review; Plan 4):
- in a header, footer or banner-position line after a cited document name, a capitals marking that is not the first
  token after the name (`CUI_SSP_v1.2 Rev A NOFORN`), and a dissemination marking in lower case or spaced
  (`CUI_SSP_v1.2 sp-propin`, `SP-propin`, `S P-PROPIN`): the capitals rule is case-sensitive;
- a file name whose prefix uses a letter that looks like I or l but is neither (`CUǀ_SSP_v1.0.docx`, a dental click)
  is read as an unprefixed title, not as a CUI_ name (folding l and 1 there would refuse names such as
  `Cul_de_sac_v1.0`);
- some all-caps words in Cyrillic or Greek letters that look Latin are refused in banner positions (`СУ1 Отчёт` reads
  as a CUI line), a false alarm in the safe direction.
- The wrong banner is looked for in headers, footers, the first and last lines (and every Markdown line), not in a
  docx body, an xlsx cell or the middle pages of a PDF (a `(CUI)` portion mark there passes; Plan 4).

### The request body limit is the application's (P3-D6)

httpd's own `LimitRequestBody` for the chp_ledger route does not take effect under the php-fpm handler (lab rounds 1
and 2): a 97 MiB body reaches PHP. The control is chp_ledger's own check: a publish of more than 64 MiB (document and
reader PDF together) is refused with HTTP 413 before anything is spooled.

### Server-side residuals (final review A; Plan 4)

- **An account made by a Bearer has no groups (P3-D3 residual).** user_oidc creates a NextCloud account from a
  `chp-doc` Bearer for a person who never signed in on the web; nothing in user_oidc stops that without stopping first
  sign-ins too. Such an account has no groups, so it can read nothing. Its requests are refused with a plain "sign in
  once in the browser" text and an alert (Wazuh 100634, level 12), and the nightly check reports it ("has no
  groups") until the person signs in on the web.
- **The Compliance areas are not compared with the ledger.** The ledger records every publish, and only
  `chp-publisher` can write the areas, but nothing yet checks that the files in the areas are exactly the ledgered
  ones (Plan 4, with an alert on any `chp-publisher` sign-in).
- **Results are never pruned.** `/var/lib/chp-docs/out` keeps one small result file per request (no tokens, no file
  bytes); it grows slowly and is not cleaned up yet.
- **Check 82 can hold up the monitor.** While a long publish holds the ledger lock, check 82 waits up to about 4
  minutes (its `verify` and `pending` each wait up to 2 minutes for the lock); the monitor has no per-check timeout
  yet, so the rest of that run waits too.

## Limits of use

- **Download and re-upload.** A person who can download CUI can upload it elsewhere. The owner accepted this as an
  insider risk. Every download and upload is logged. The site rule: CUI from the document server is never uploaded
  outside the CUI folders (SSP 3.1.3).
- **FCI is marked FCI** (owner decision, 2026-11-20). An `FCI_` document carries the banner `FCI` at the top and
  bottom of every page and no CUI designation block. A CUI banner on it is refused, and so is an FCI banner on a
  `CUI_` document. `FCI_` controlled documents are published into `CUI/Compliance`, so they carry the CUI tag (tagging
  is by folder); the nightly tag check accepts that in CUI and Archive only. `chp-site doc new --fci` needs the FCI
  templates (`/usr/share/chp-templates/doc/fci/`, chp-templates 1.4.0-2).
- **Time comes from the CHP server** (owner decision, 2026-11-20). Workstations use the server as their only time
  source. The server serves NTP to `SUBNET` only: 123/udp is the owner-approved exception to "no new network port".
  The server's chrony therefore leaves `chronyd_client_only` off; the server is scanned with the tailored profile in
  `/usr/share/chp/scap/chp-server-cui-tailoring.xml`. It unselects exactly two rules, each with its reason:
  `chronyd_client_only` (the owner's NTP decision) and `sysctl_user_max_user_namespaces` (the existing ISO deviation:
  systemd's unit sandboxing needs user namespaces; the reason is quoted from `docs/dc2-planning/dc2-cui-tailoring.xml`).
  A scan with the stock profile reports both as failed. Workstations keep the stock profile, so their stock scan
  still reports the namespaces rule as failed (the same `%post` change is on every host). The server's chrony
  listens on its site address and, for IPv6, on loopback only. On an installed site, run
  `chp-site time-sync` on the server first, then on each workstation: until then the new egress table cuts the
  workstation off from `NTP_UPSTREAM` and check 20 alerts. If the server's upstream fails,
  it serves its own clock (`local stratum 10`), so the site keeps one time; check 20 on the server still alerts on
  the server's own offset.
- **Server memory.** The server needs at least 8 GiB.
- **Alert text carries CUI file names and paths** and goes to `ALERT_HOOK`. The site delivers it only inside the CUI
  boundary.
- **Hand-off of a draft** to the approver is a browser upload to an ordinary CUI (or Internal) folder and a download
  by the approver. The approval is bound to the file's sha256, so the transport needs no trust. The approver must not
  run `doc checkout`.
- **Workstations.** `KillUserProcesses=yes` and an hourly `disable-linger` apply to all accounts, so an
  administrator's `tmux` or `screen` session ends at logout. The whole workstation is confined to the site server and
  the site resolver, Firefox included. A failed egress table at boot leaves only loopback (Wazuh 100628, level 12,
  written while the link is down, so it may never arrive; the first live signal is the server's agent-disconnected
  check 71). After recovery one line `EGRESS RECOVERED after LOCKDOWN` (Wazuh 100635, level 12) says when it began
  and why, sent once the agent is connected again (lab 11c, P3-D7). A stopped agent holds it too (P3-D15). After 60
  minutes it is sent anyway, with an ALERT from check 83. A workstation with no Wazuh agent installed (no unit, no
  binary, and rpm says the package is not installed) has nothing to wait for and reports at once.
- **The reader PDF** is made with ONLYOFFICE's converter, which the vendor does not document as a supported interface.
  ONLYOFFICE must have been started once by the person who publishes.
- **The reader PDF is not compared with the approved document** (final review A I-3). The approval binds the
  document's sha256. The server checks the reader PDF's marks and records its sha256 (`pdf_sha256`), but not that
  its text is the approved document's: an author could publish a reader PDF with other content. The approved
  document is the record. Plan 4 adds a text-equivalence check. The reader PDF itself cannot be checked out, created
  or published as a document of its own.
- **The clock.** The sign-in is refreshed 60 seconds before it ends, which assumes chrony keeps the workstation
  clock right (with the CHP server as its only source).
- **Pending requests.** A command that ends with exit 3 is run again with the same words; its request id is kept
  across `chp-site doc logout` (`chp-site doc logout --forget` drops the kept ids).

## Alerts that surprise people

- The first `chp-site documents enable` raises rule 100623 (level 12) five times: the break-glass admin account
  `ncadmin` is made and added to `admin` (two lines), and the appender's publish account `chp-publisher` is made and
  added to `chp-users` and `cui-users` (three lines; lab 11c, P3-D5). Tell the ISSO first.
- Running `chp-site documents check` by hand outside 03:05-03:45 enables `chp-canary` and raises rule 100609
  (level 12), like an intrusion.
- Rule 100629 (level 12) pages once for each new CUI reader's first sign-in.
- A missed night (the server was off at 03:10) is not caught up: there is no tag check and no canary for up to about
  48 hours. Check 81 alerts when its result is older than 26 hours.
- Events that NextCloud writes while the Wazuh manager restarts may not be analysed. The audit file keeps every line.
- Check 82 reports "not checked this run" when the appender holds the ledger lock. It alerts after 4 runs in a row.
